# RCA — Driver Live Mode heartbeat 409 "Driver is offline" (cargoone.co.uk)

Deployment: cargo-repo-bridge (prod, FastAPI+React+Mongo, cloudflare frontend)
Active run: 7f49054c-5239-4be5-bb62-dd9ed56f03a4 | tier_0 | template fastapi_react_mongo_shadcn_base_image
Mode: READ-ONLY diagnosis. Nothing was changed/deployed.

## Symptom
Driver iOS app in Live Mode receives HTTP 409 "Driver is offline" from POST /api/driver/live/heartbeat during an active online session; the app still shows "online".

## What I collected from production

### (2) Pods / databases — ANSWERED
- 2 backend replicas (tier_0, replicas=2) behind one service.
- SINGLE MongoDB: db_name = `cargo-repo-bridge-test_database` (one Atlas DB, served to both pods via the same MONGO_URL secret).
- Mongo client is `AsyncIOMotorClient(MONGO_URL)` with NO explicit read preference (server.py:148-149) → default = PRIMARY reads. Motor default write concern is acknowledged (w=1).
- CONCLUSION: "online and heartbeat hitting different DBs" is NOT happening. Both pods read/write the same primary; reads are read-after-write consistent. This is not a multi-DB or stale-secondary-read bug under normal operation.

### Server-side writers of live_online — VERIFIED by full-backend grep
- live_online set TRUE: POST /driver/live/online (server.py:2701) and the heartbeat conditional update (2739, only when already True).
- live_online set FALSE: ONLY POST /driver/live/offline (server.py:2722).
- No scheduler/cron/background sweeper anywhere (no APScheduler/celery in requirements.txt; grep for create_task/while True/cron found nothing that touches live_online). All other live_online references (2735, 2751, 2781, 2934) are reads.
- get_current_user resolves the user by {"id": payload["user_id"]} (server.py:430) and 401s if not found, so the user doc ALWAYS exists with that id. /online does update_one({"id": user["id"]}, {$set: live_online:True}); heartbeat does find_one({"id": user["id"]}). Same key, same doc. Therefore after a 200 /online, the DB flag IS true, and a subsequent heartbeat MUST read true — UNLESS something flips it false in between.

### Client behaviour — VERIFIED by source
- iOS (mobile/apps/driver/src/screens/LiveMode.tsx): goOffline() is called ONLY from the "Go Offline" button onPress (line 613). NO AppState/background/visibility/unmount handler calls /offline. The heartbeat loop (lines 379-428) on ANY error (incl. 409) only sets a local error string and reschedules another heartbeat — it does NOT revert `online` state. => UI stays "online" while every heartbeat 409s. This is the exact symptom presentation.
- Web (frontend/src/pages/portal/driver/Live.jsx + LiveClassic.jsx): same — /offline only on explicit button; heartbeat cleanup only clears timers, no /offline on unmount/pagehide.

## Root cause (evidence-backed)
`live_online` is a SINGLE shared boolean on the user document with NO per-device / per-session scoping. The backend flips it false ONLY on an explicit POST /driver/live/offline. Given no server-side sweeper and no client auto-offline, a mid-session heartbeat 409 means an explicit /offline reached that ACCOUNT from some session while the iOS app still believed it was online. Because the flag is account-global and shared across all concurrent sessions (web portal tab, a second device, or a stale/duplicate client instance), an /offline from any one of them flips the one flag and the iOS heartbeats then correctly 409. The iOS client compounds the symptom by swallowing the 409 and never reverting its UI, so the app looks stuck "online".

Supporting evidence: the one currently-online driver (driver1) shows live_updated_at advancing for 7 days => heartbeats normally succeed; the 409 is therefore an interference/transient event tied to a concurrent /offline on the same account, not a permanent per-user breakage.

Secondary (lower-probability, unverifiable here): an Atlas primary failover rolling back a non-majority-acknowledged live_online=true write would also present as a persistent 409 until the next /online. Not reproducible without live infra; noted for completeness.

NOT the cause (ruled out): different DBs per pod (single DB confirmed); stale secondary reads (primary read preference); a server-side auto-offline sweeper (none exists); duplicate/mis-keyed user docs (driver1 has exactly one doc, matched by the same `id` used everywhere).

## Reproduction status
NOT reproduced at runtime. This is a concurrency/design issue requiring a live DB + two concurrent authenticated sessions + real secrets, which the eph sandbox cannot provide (no app secrets, no live Atlas). Diagnosis is from source inspection (eph sandbox, read-only) + production DB state (mongo_query) + log inspection. No eph runtime verification is claimed.

## Recommended fixes (for E1 / source owner — NOT applied here)
1. (Code) Make heartbeat self-healing for an authenticated, approved, active driver: instead of 409 when live_online is falsy, either re-assert online (upsert live_online=true + refresh live_online_since) or return a benign 200 so a live session is never silently dropped. File: backend/server.py, driver_heartbeat (~2728-2744).
2. (Code) Scope presence per device/session rather than a single account-global boolean (e.g. a live_sessions subdoc/collection keyed by device/session id; account is "online" if any session is). Prevents one session's /offline from killing another's. File: backend/server.py live endpoints (2625-2745) + clients.
3. (Code) iOS client must stop silently retrying on 409: on heartbeat 409 either revert the UI to offline (truthful state) or automatically re-call /online. File: mobile/apps/driver/src/screens/LiveMode.tsx heartbeat loop (~386-401).
4. (User) Confirm whether the affected driver has a second concurrent session logged into the same account (web portal tab left open, or a second device) that issued a Go Offline — this is the most likely trigger given the account-global flag.
5. (Platform/infra, optional) To close the failover edge, use write concern majority for the live_online=true write; and to get the log evidence that's currently missing, retain/ship app access logs so online/offline/heartbeat sequences with UA/IP are queryable.
