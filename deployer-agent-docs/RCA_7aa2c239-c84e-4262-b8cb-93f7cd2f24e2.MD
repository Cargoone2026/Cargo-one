# RCA — IndexNow never submits for https://cargoone.co.uk

Deployment: cargo-repo-bridge (e847aa95-43db-46e0-9336-52335babb956)
Active run: 7aa2c239-c84e-4262-b8cb-93f7cd2f24e2 (redeploy, success)
Frontend type: cloudflare (frontend built in Cloud Build, served from R2)

## Problem statement
Bing Webmaster shows zero IndexNow submissions. `frontend/scripts/indexnow.mjs` only pings when `process.env.INDEXNOW_ENABLED === "true"`. It runs as a `postbuild` hook during `yarn build`. User added custom secret `INDEXNOW_ENABLED` via Secrets panel (env_file "backend", env_mode "shared").

## Root cause (proven)
The IndexNow ping runs at **frontend BUILD time** (the `postbuild` hook inside `build-frontend-artifacts.sh` → `yarn build`), but the custom secret `INDEXNOW_ENABLED` is **only injected into the backend RUNTIME pod environment**, never into the Cloud Build frontend build step. So `process.env.INDEXNOW_ENABLED` is undefined during the build and the script always skips.

Two independent reasons it fails, both confirmed:

### 1. Wrong injection point (primary)
- Pipeline order: `build_image` (step 3, where yarn build + postbuild run) executes BEFORE `write_secrets` (step 5). Custom secrets are composed and written in write_secrets and target the **production pod env**, not the Cloud Build environment.
- `build-frontend-artifacts.sh` (the actual production frontend build script) shows the only env available at build time is platform build args: `BACKEND_URL`, `DEPLOYMENT_NAME`, `TAG`, `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_ARTIFACTS_BUCKET`, `ARTIFACT_REGISTRY_*`, `PREVIEW_DOMAIN`. No custom/user secrets are passed in.
- The secret is tagged env_file "backend" → it lands in the backend runtime env only. `frontend/.env` in source does NOT contain `INDEXNOW_ENABLED` (verified), and even if it did, `indexnow.mjs` reads `process.env` directly (no dotenv load), so a frontend/.env entry would not reach it either.
- Sandbox reproduction (run 7aa2c239, source at /app/scratch): running `node scripts/indexnow.mjs` with the var unset prints exactly:
  `[indexnow] skipped (INDEXNOW_ENABLED is not true)` — the build-step reality.

### 2. Stored secret value is not exactly "true" (secondary)
- `list_secrets` (active run): `INDEXNOW_ENABLED` is_empty=false, but `matches_expected=false` against both `"true"` AND `"false"`. So the stored value is non-empty and is NOT the exact string `"true"`.
- The script uses strict `=== "true"`. Sandbox: `INDEXNOW_ENABLED=True` (capital T) also prints the skip line; only `INDEXNOW_ENABLED=true` fires (it then POSTed 870 URLs and got HTTP 403 from the sandbox IP — proving the fire path works, the 403 is just the untrusted sandbox origin).

So even if the secret WERE reaching the build step, the current value would still skip.

## Answers to the 4 questions
1. **Does INDEXNOW_ENABLED exist in prod and its value?** Yes, it exists and is non-empty on the active run. Its value is NOT the exact string `"true"` (and not `"false"` either) — value is never returned, but the strict `=== "true"` check fails against it.
2. **Injected into the FRONTEND build step env, or only backend runtime?** Only backend runtime. Custom secrets are written in write_secrets (step 5) into the pod env, after the image is already built (build_image, step 3). The Cloud Build frontend build has no access to user secrets. It is tagged env_file "backend", so it never reaches frontend either.
3. **What does the production [indexnow] build line say?** Could not read the production build log directly — get_build_logs returned `build_lookup_limit` (CodeBuild build object not resolvable) on every recent run. Based on the code path (env absent at build), the emitted line is `[indexnow] skipped (INDEXNOW_ENABLED is not true)` — reproduced verbatim in the sandbox. Reported as INFERRED, not read from the live build log.
4. **Platform-supported way to set an env var for the prod frontend build only?** No user-facing way. Custom secrets are runtime-only and are injected after the image is built; they never reach the Cloud Build frontend build step. The only way to influence the build env is a deployment-manifest edit to `build-frontend-artifacts.sh` (platform/deployer-level, hardcoded — not a secret, and it still could not read the user's secret value at build time). CRA only inlines `REACT_APP_`-prefixed vars from `frontend/.env`; a plain Node postbuild script reading `process.env` would not receive them anyway.

## Recommended fix
- **Code (E1):** Move the IndexNow submission out of the build-time `postbuild` hook into a **backend runtime** task (startup hook or scheduled job), where `INDEXNOW_ENABLED` actually exists in the environment. Alternatively, drive the ping from the backend reading `process.env.INDEXNOW_ENABLED` there. (Note: Bing/IndexNow may 403 from certain origins; verify the prod backend egress IP is accepted — the sandbox 403 is expected.)
- **User:** Set `INDEXNOW_ENABLED` to the exact lowercase string `true` in the Secrets panel (current value is not exactly "true"). This alone will NOT fix build-time execution — it only matters once the ping runs in the backend runtime per the code change above.
