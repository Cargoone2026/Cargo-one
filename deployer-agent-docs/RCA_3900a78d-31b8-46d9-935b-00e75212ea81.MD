## Route sort order (backend/server.py `GET /bookings/mine`, line 3926)
```python
bookings = await db.bookings.find(q, {"_id": 0}).sort("created_at", -1).to_list(200)
```
`/bookings/mine` returns the caller's bookings sorted by **`created_at` descending (newest first)**, cap 200. So when the iOS app "takes the FIRST element whose job_id matches", it is selecting the booking with the **most recent `created_at`** for that job.

## Does any job have MORE THAN ONE booking?
**No.** Across every ASAP job inspected (the 5 driver-assigned and the 5 next-most-recent driverless), **each job_id maps to exactly one booking document.** There are no duplicate/stale bookings competing to be "first".

## Which booking would `/bookings/mine` place first?
Since each job has a single booking, the "first element whose job_id matches" is simply that one booking — and for the two last-3-day jobs it is the fully-progressed one (`status=pod_uploaded`, `payment_status=paid`). The newest-first sort cannot select a stale earlier booking because none exists.

## Conclusion
The duplicate-booking hypothesis is **not supported by production data.** For the stuck-looking ASAP jobs (`797fb26a`, `4d8d78a2`), the backend state is fully consistent and progressed: `job.status=pod_uploaded`, the single booking is `pod_uploaded`/`paid`, driver assigned on both job and booking. This matches what the web portal shows.

Therefore the iOS app displaying "Payment required"/"Driver accepted" while the DB (and web) show `pod_uploaded`/`paid` is **not a server data problem** — it points to a client-side issue on the Customer iOS app (stale cached booking state / polling or refresh of `/bookings/mine` not re-fetching, or the app keying off a cached snapshot). Confirm by having the affected iOS client hard-refresh / re-fetch `/bookings/mine` and compare the returned `status`/`payment_status` against the screen.
