# RCA — cargoone.co.uk (cargo-repo-bridge) Cloudflare 520 incident

**Scope:** Read-only diagnosis. Nothing was changed.
**Live run / pods inspected:** active run `3900a78d-31b8-46d9-935b-00e75212ea81` (cluster target-7, namespace customers-app). This is the run that was serving during the incident.
**Template:** fastapi_react_mongo_shadcn (FastAPI backend behind nginx:8080, frontend on Cloudflare). **Tier:** tier_0 "Starter" — cpu 50m/limit 250m, **memory 200Mi/limit 512Mi, 2 replicas, HPA disabled**.

## Window clarification
The instability maps exactly to the **BST-converted window: ~12:45–13:10 UTC on 2026-10-12** (= 13:45–14:10 BST). "Today" is **Oct 12**, not the Oct 11 deploy day. The literal-UTC window (13:45–14:10 UTC) shows **no** origin issues — the last K8s event is 13:06 UTC (scaled back to 1 replica, stable). So the incident is the BST interpretation.

## (1) Pod status / events in the window
**OOMKill confirmed — this is the root cause.**
- Pod `...-5fjxv`: `last_termination = OOMKilled (exit 137)`, started 12:57:21Z, finished **12:58:19Z**, `restart_count = 2`.
- Liveness probe degradation on 5fjxv from **12:49:59Z** (503), then **12:57:19Z** `Liveness probe failed ... read: connection reset by peer`, then **12:58:19Z** `Liveness probe failed ... EOF`, then `BackOff restarting failed container` at 12:58:28Z.
- Second replica `...-lds7h` was scaled up at **12:56:53Z** but **failed its startup probe** (`connection refused` 12:57:54–12:58:19, then `HTTP 503` 12:58:24–12:58:39) — i.e. it was NOT ready while 5fjxv was OOM-restarting.
- Net effect: for roughly **12:57–12:59 UTC both replicas were simultaneously unavailable** (one OOMKilled+backing off, the other not yet past startup). 
- Replica count oscillated 1↔2 (up 12:18, down 12:28, up 12:56, down 13:06) despite HPA disabled — consistent with rollout/restart churn, not a user deploy (no deploy run exists on Oct 12; last deploy was Oct 11 21:40 UTC).
- No `FailedScheduling`, no `ImagePullBackOff`, no eviction. Kill reason is memory, not disk/node pressure.

## (2) Backend logs in the window
- **No 5xx present in retained logs.** Status histogram over the window = 200s plus internal `GET /health 404` (benign — nginx proxies /health to backend:8001 and treats 4xx as healthy).
- There is a **gap in request logging around 12:57–12:59 UTC** — consistent with the process being dead (killed), not with it serving errors. OOM kills do not emit app-level error lines; the worker dies mid-response.
- Workload shape that drives the memory pressure (single uvicorn worker, `--workers 1`): nearly **every** `GET /api/tracking/{id}` triggers an outbound `GET maps.googleapis.com/.../distancematrix` call, plus **Expo push fan-out** (`POST https://exp.host/--/api/v2/push/send`) on status/message events. Sustained customer + driver polling on one worker at a 512Mi ceiling is the proximate cause of the OOM.
- **ASAP offer-alert task** (`_asap_offer_alert_loop` / `_send_asap_offer_alerts`): no error lines from it appear in the retained window. Cannot be positively cleared from logs alone — if it runs a background loop that accumulates per-offer state or holds large result sets in memory, it contributes to the same memory envelope that OOM'd. Recommend E1 review it for memory growth and unawaited/large fan-out.
- Benign noise (NOT the 520 cause): `AttributeError: module 'bcrypt' has no attribute '__about__'` + `WARNING:passlib...trapped error reading bcrypt version` (cosmetic passlib/bcrypt version probe). Also `WARNING:services.email: email FAILED ... err=API key is invalid` (new_message + cash_on_delivery_reminder templates) — email/SendGrid key is invalid; unrelated to the outage but a separate real defect.
- `STRIPE_API_KEY loaded prefix=sk_test_` — note production is running a **Stripe TEST key** (separate observation, not incident-related).

## (3) 520 attribution — origin-side, not client-side
The 520s are **consistent with origin-side failure**, not a client/hotspot problem. Cloudflare emits 520 when the origin returns an empty/invalid response. During 12:57–12:59 UTC the origin was: one pod OOMKilled and in CrashLoop/BackOff, the other not past startup, with liveness probes seeing `connection reset by peer` and `EOF`. That is precisely an origin closing/refusing connections → empty response → 520. The customer 520s on `/api/auth/me`, `/api/bookings/mine`, `/api/jobs/mine`, `/api/notifications`, `/api/messages/summary` and the driver "network failure" on `POST /api/tracking/{id}` all fall in/around that dead window. The 4G/5G hotspot is incidental.

## (4) POST /api/tracking/{bookingId} — were points received & saved?
**Yes, for the driver's active booking, up until the job completed.**
- Driver `335cb4ff-709d-4f2a-919e-7ae6299abafe`'s most recent (and only Oct-12) booking: `_id 6accd7f7...`, **`id = 19f1a973-b91e-498d-b585-c7b4fc70d193`**, service_type `breakdown_recovery`, created 12:52:07Z, status `pod_uploaded`, updated **12:55:48Z**. (No `asap`/`is_asap`/`booking_mode` field exists on the doc under those names; ASAP state is not a boolean flag on bookings.)
- `tracking` collection (keyed by `booking_id`, with `lat`/`lng`/`created_at`/`driver_id`): **12 points saved** for this booking, from **12:53:50Z → 12:55:35Z**, all driver 335cb4ff. Cadence a few seconds to ~30s apart — normal, no anomalous gap.
- The last point (12:55:35Z) is ~13s before the booking reached `pod_uploaded`/completed at 12:55:48Z, and **~1.5 min before** the OOM crash at 12:57–12:58. So tracking stopped because the job finished, **not** because of the outage. **No lost/unsaved tracking points are attributable to the incident for this booking.**
- The driver "network failure" on tracking POSTs the user saw was most likely pings attempted during the 12:57–12:59 dead window (for a subsequent/next action), which never reached the origin — those simply produced no DB write and no server log, by definition.

## Retention / what could NOT be verified
- Loki retained the incident window; however raw per-request logs during the ~12:57–12:59 process-death are absent (expected — the worker was killed). `last_termination` (OOMKilled/137) survives K8s event expiry and is the authoritative kill signal.
- Exact peak RSS at the moment of OOM is not available (no in-cluster memory profiler via these tools) — the OOMKilled reason at the 512Mi limit is the evidence, not a measured curve.
- `list_secrets` is scoped to the live run only; cannot assert any key's state as it was on a past run.

## Recommended remediation
1. **Tier (User):** OOM at the tier_0 512Mi ceiling is confirmed. Raise the tier in Deployment Panel → Resources (tier_1 "Launch" or higher) for more memory headroom + CPU. This is the direct fix for the 520s.
2. **Code (E1):** Reduce the per-request memory/CPU envelope: cache/throttle the Google Distance Matrix call so it isn't fired on every `/api/tracking` GET; make the Expo push fan-out and the `_asap_offer_alert_loop`/`_send_asap_offer_alerts` background task bounded (await properly, avoid holding large lists, batch sends). Consider whether `--workers 1` is adequate once memory is raised.
3. **Secondary (User), not incident-related:** email/SendGrid API key is invalid (`email FAILED ... API key is invalid`); Stripe is running a `sk_test_` key in production. Both are real but separate from the 520 incident.
